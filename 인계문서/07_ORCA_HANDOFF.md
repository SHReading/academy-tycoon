## 작업 A — sim-core (`src/core/`) · 최우선

다른 모든 트랙이 여기 타입에 의존한다. **A-1이 끝나기 전에 B·C·D를 시작하지 않는다.**

### A-1. 타입 + RNG (여기까지가 병렬 해금 조건)
- `types.ts` — `GameState`, `Academy`, `TeacherCard`, `EventCard`, `HeadlineTemplate`, `Action`, `TurnResult`, `Archetype`, `ClassTier`, `Subject`, `Trait`
  - `schema/*.json`과 필드명·enum이 **정확히 일치**해야 한다
  - 스키마 3종의 `title`이 타입명이다 — `TeacherCard`·`EventCard`·`HeadlineTemplate`.
    목록과 스키마가 어긋나면 **스키마가 맞다** (8/13 `HeadlineTemplate` 누락 발견해 추가)
- `rng.ts` — mulberry32 시드 RNG. 같은 시드 → 같은 수열 테스트 포함
- **완료 정의**: `npm run typecheck` 통과 + RNG 결정성 테스트 통과 + 타입이 스키마와 1:1 대응

### A-1b. 구현 계약 (8/13 코디네이터 확정 — 밸런스 아님, 구조)

트랙 B·D가 같이 쓰는 계약이다. **여기 정의된 이름을 그대로 쓴다.**

```ts
type Contract = { teacherId: string; price: number; remainingTurns: number }  // 낙찰가는 6턴 고정비
type OperationOption =
  | 'SELF_STUDY'     // 자습 감독 강화
  | 'COUNSELING'     // 담임 상담 확대
  | 'SCHOLARSHIP'    // 장학금 확대
  | 'TUITION_HIKE'   // 수강료 인상
  | 'NONE'           // 아무것도 안 함
```

`Academy`에 추가할 필드: `contracts: Contract[]`, `option: OperationOption`, `lastBidTurn: number | null`,
`pendingEffect: EventEffect | null`. **`assignments`는 이미 있으니 재사용한다.**

| 미정이던 것 | 확정 |
|---|---|
| `BID` 처리 | 리듀서 안에서 **즉시 낙찰까지 끝낸다.** AI 2사 입찰가는 05 문서 4절 손규칙(FRANCHISE ×1.2 / LEGACY ×1.1, 잔액 40% 상한)을 RNG와 함께 결정론적으로 계산. 최고가 낙찰, 동액이면 평판 우선. pending 상태를 따로 두지 않는다 |
| 이벤트 추첨 | `SETTLE` 마지막에 `weight` 가중 추첨으로 1장. **RNG 소비는 정확히 1회** |
| 이벤트 효과 적용 | 뽑은 효과를 `pendingEffect`에 저장하고 **다음 턴 계산에서 소비 후 null로 되돌린다.** reputation·cash는 절대값, churn·applicants·grade는 비율 |
| `BASIC_CLASS_SPECIALIST` 이탈률 감소량 | **−0.03 (제안값)** — `balance.ts`에 두고 트랙 D 시뮬로 검증한다 |

### A-2. scoring.ts
`01_GAME_DESIGN.md` 4절 단계 4의 **7단계를 순서대로 그대로** 구현한다. 순서를 바꾸지 않는다.
- **완료 정의**: 손계산한 케이스 3개와 결과가 일치. 정산 1회 16ms 이내

### A-3. reducer.ts
`(GameState, Action) => GameState` 순수 함수. 액션은 `BID` / `ASSIGN` / `OPTION` / `SETTLE` 4종.
- **완료 정의**: 같은 시드 + 같은 액션 시퀀스를 100회 돌려 결과가 전부 동일

### A-4. ai.ts
경쟁 학원 2곳의 입찰·배치 정책. **1차 구현은 `05` 문서 4절의 손규칙을 그대로 옮긴다.**
영리하게 만들지 않는다 — 강한 AI가 아니라 **읽히는 AI**가 목표다.

### A-5. telemetry.ts
`02_TECH_SPEC.md` 7절의 `ScoreSink` 인터페이스. 기본 구현은 no-op. **실제 전송 구현 금지.**

## 작업 B — ui (`src/ui/`, `src/styles/`) · A-1 이후

### 화면 4개가 전부다
1. 학원 선택 (3개 카드, 탭 1회)
2. 입찰 (시장 카드 4장 + 입찰가 입력)
3. 반 편성 + 운영 옵션 (상위/중위/기초 × 4슬롯, 옵션 택1)
4. 정산 결과 (**헤드라인 3줄이 주인공**, 숫자는 보조)

### 타협 불가 (01 문서 7절)
- 로딩 화면 없음 / 튜토리얼 화면 없음 — 규칙은 버튼에 붙은 한 줄 설명으로 이해되어야 한다
- 1턴 90초, 1판 5분 이내
- **모바일 세로 우선**, 터치 타깃 44px 이상
- 한 화면에 동시에 보이는 숫자 **7개 이하**
- 게임 오버 후 **한 번의 탭으로 재시작**

### 헤드라인은 P2 필수 기능이다
"나중에 붙이자"의 대상이 아니다. 시연에서 관객이 규칙을 몰라도 상황을 이해하게 만드는 장치이자,
심사 항목 Presentation에 대한 이 프로젝트의 유일한 답이다.

## 작업 C — content (`src/content/`) · 스키마 확정 이후

### 목표 물량
강사 카드 200장 / 이벤트 카드 150장 / 헤드라인 템플릿 100개

### 배치 규칙
- **배치 1개 = 20장.** 배치별로 id 번호 구간을 사전 배정해 충돌을 막는다 (배치1 = `t_0001`~`t_0020`)
- 매 배치 생성 직후 `npm run validate:content` 실행. **통과분만 머지한다**
- 분포 조건을 생산 지시에 반드시 포함한다 (03 문서 3절)

| 축 | 목표 분포 |
|---|---|
| 과목 | 국 25% / 수 30% / 영 25% / 탐 20% |
| 강의력 | 1~2가 40%, 3이 35%, 4가 20%, 5가 5% |
| 요구 연봉 | 강의력 5는 상위 10% 구간에만 배정 |
| 특성 | 승인된 종류 균등 배분 |

### 절대 금지
- 실존 학원·강사·기업명. 연상시키는 표현도 포함
- 특정 실존 사업자를 열위로 묘사하는 문구
- 검증 실패분을 손으로 고쳐 통과시키기 — **반려하고 재생성한다**

## 작업 D — harness (`src/harness/`, `scripts/`) · A 이후

```
npm run sim -- --games 100000 --seed 1
```

**출력이 답해야 하는 질문은 정확히 3개다** (01 문서 6절)

| # | 질문 | 실패 판정 |
|---|---|---|
| 1 | 무입찰 전략이 지배전략인가 | 무입찰 승률 > 40%면 게임이 죽은 것 |
| 2 | 상위반 몰빵 / 중위반 확장 중 하나가 항상 이기는가 | 한쪽 승률 > 60% |
| 3 | 3개 아키타입 승률이 40:30:30 안에 들어오는가 | 최대 편차 > 15%p |

**추가 출력**: 턴당 입찰 성공률, 게임 길이 분포, 조기 폐원 비율

**하지 않을 것**: 결과를 보고 밸런스를 스스로 고치는 것.
문제를 **발견해서 보고**하는 것이 이 트랙의 일이고, 고칠지 말지는 사람이 정한다. (03 문서 1절)
