**착수 즉시 공식 사이트에서 마감일과 접수 상태를 재확인할 것.** 보도자료 기준 접수는 8/4–8/26이지만, 사이트에서 직접 확인한 것만 신뢰한다.

## 2. 플레이 링크 요건 (하나라도 실패하면 심사 불가)

- ☐ 브라우저에서 바로 실행되는 웹 빌드
- ☐ 심사 기간 내내 접속 가능
- ☐ 별도 승인·로그인 없이 접근 가능
- ☐ 별도 제약 없이 플레이 가능
- ☐ 조작법과 실행 방법 안내가 게임 안에 있음
- ☐ **시크릿 창에서 검증 완료**
- ☐ **다른 기기 모바일에서 검증 완료**

## 3. 가산점 항목 (선택이지만 반드시 낸다)

### 데모 영상 (3분 이내)
구성: 게임 소개 → 실제 플레이 → 핵심 기능. 실제 플레이 화면이 포함되어야 한다.

권장 배분
- 0:00–0:20 훅. "재수학원 원장이 되어 스타 강사를 뺏고 뺏긴다"
- 0:20–1:40 1턴 실제 플레이. 입찰에서 손이 멈추는 순간을 보여준다
- 1:40–2:30 6턴 압축, 헤드라인이 쌓이는 장면
- 2:30–3:00 개발 방식 한 컷 (병렬 트랙, 카드 생산 파이프라인)

### Codex 활용 설명
공식 질문 4개에 답하는 형식으로 쓴다. 03 문서의 PR 기록과 DEV_LOG에서 그대로 뽑는다.

- ☐ Codex를 어디에 사용했는가
- ☐ 어떤 기능을 구현했는가
- ☐ 어떤 문제를 해결했는가
- ☐ **사람이 직접 결정한 부분은 무엇인가** ← 여기가 차별점. 규칙 설계·밸런스 판정·스코프 컷이 전부 사람이었다는 점을 구체적 사례로 쓴다

## 4. 게임 소개 200자 초안

> 스타 강사는 한정되어 있고, 내가 지르지 않으면 경쟁 학원이 데려간다. 재수학원 세 곳이 같은 지원자를 놓고 3년간 경쟁하는 경영 시뮬레이션. 강사를 입찰로 영입하고, 상위반과 중위반 중 어디에 배치할지 결정한다. 한 판 5분, 설치와 로그인 없이 브라우저에서 바로.

(공백 포함 글자 수를 제출 전 반드시 세어볼 것)

## 5. 3분 엘리베이터 피치 뼈대

| 구간 | 내용 |
|---|---|
| 0:00–0:20 | 한 문장 훅 + 왜 이 소재인지 (관객이 이미 아는 세계) |
| 0:20–1:20 | 라이브 시연. 입찰 한 번, 배치 한 번, 헤드라인 한 번 |
| 1:20–2:10 | 설계 관점. 제로섬 입찰이 왜 코어인지, 무엇을 일부러 뺐는지 |
| 2:10–2:50 | 개발 방식. 사람이 결정한 것과 병렬 생산으로 넘긴 것 |
| 2:50–3:00 | 확장 계획 한 줄 (랭킹·리플레이 연동 지점) |

**시연은 반드시 오프라인에서도 돌아가야 한다.** 현장 네트워크를 신뢰하지 않는다. 로컬 빌드를 노트북에 준비하고, 백업으로 화면 녹화본을 가져간다.

## 6. 제출 전 최종 점검 (8/25)

- ☐ 실명 필터 최종 실행. 코드·콘텐츠·문서·영상 전체에 실존 학원/강사/기업명 0건
- ☐ 회사 데이터·내부 문서 흔적 0건
- ☐ 링크가 시크릿 창, 모바일, 다른 네트워크에서 열림
- ☐ 로딩 화면 없이 즉시 시작됨
- ☐ 게임 오버 후 재시작 동작
- ☐ 6턴 완주에 5분 이내
- ☐ 썸네일 16:9, 10MB 이하
- ☐ 데모 영상 3분 이내
- ☐ 저장소가 제출 후에도 유지됨 (링크 생존)
- ☐ 8/31 월요일 일정 확보

## 7. 떨어져도 남는 것

- 배포된 플레이 가능한 웹 게임 링크 하나
- 재사용 가능한 병렬 콘텐츠 생산 파이프라인
- 결정론적 시뮬레이션 코어 + 밸런싱 하네스

**이 세 개는 심사 결과와 무관하게 확보된다.** 이것이 이 프로젝트의 출구 설계다.
