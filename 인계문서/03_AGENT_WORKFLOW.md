# 03. 에이전트 워크플로

이 문서는 개발 방식인 동시에 **제출 항목 "Codex와 함께 게임을 만든 과정"의 원재료**다. 여기 기록이 쌓이면 제출 문서를 따로 쓸 필요가 없다.

---

## 1. 역할 분담

| 주체 | 담당 | 담당하지 않는 것 |
|---|---|---|
| **사람 (설계자)** | 코어 루프, 트레이드오프 구조, 밸런스 판정, 무엇을 버릴지 | 구현 코드 직접 작성 |
| **Claude (코디네이터)** | 스펙 유지, 태스크 분해, PR 리뷰, 트랙 간 충돌 조정 | 대량 구현 |
| **Codex (워커)** | 트랙별 실제 구현, 테스트, 콘텐츠 생산 | 게임 규칙 변경 |

**불변 규칙**: 게임 규칙과 수치는 사람이 정한다. 에이전트가 밸런스를 "개선"하는 것을 허용하지 않는다. 재미의 판단 기준은 사람에게만 있다.

## 2. 트랙 분할 (병렬 워크트리)

4개 트랙은 서로 다른 디렉터리를 건드리므로 충돌 없이 병렬 실행 가능하다.

| 트랙 | 범위 | 산출물 | 의존 |
|---|---|---|---|
| **A. sim-core** | `src/core/` | reducer, scoring, ai, rng | 없음 (최우선) |
| **B. ui** | `src/ui/` | 화면, 입력, 헤드라인 연출 | A의 타입 정의 |
| **C. content** | `src/content/` | 강사·이벤트·헤드라인 카드 | 스키마 확정 |
| **D. harness** | `src/harness/` | 대량 시뮬레이션, 리포트 | A |

**순서**: A의 타입과 스키마를 먼저 확정 → B·C·D를 동시 착수.

## 3. 콘텐츠 배치 파이프라인 (이 프로젝트의 차별점)

강사 카드 200장 + 이벤트 카드 150장 + 헤드라인 템플릿 100개가 필요하다. 손으로 쓰면 3일, 배치로 돌리면 반나절이다.

```
설계(사람)          생산(에이전트)              검증(자동)
────────────       ──────────────────         ──────────────
스키마 확정    →    배치 N개 병렬 생성    →    스키마 검증
분포 조건 지정      각 배치 = 카드 20장        값 범위 검사
                                              중복·유사도 검사
                                              실명 필터 ★
                                                   ↓
                                              통과분만 머지
```

**★ 실명 필터는 필수 검사다.** 생성된 카드에 실존 학원·강사·기업명이 섞이지 않았는지 금칙어 목록으로 자동 차단한다. 00 문서 가드레일 1의 기술적 담보.

**분포 조건 예시** — 생산 지시에 반드시 포함한다.
- 과목 비율: 국 25 / 수 30 / 영 25 / 탐 20
- 강의력 분포: 1~2가 40%, 3이 35%, 4가 20%, 5가 5%
- 강의력 5는 요구 연봉 상위 10%에만 배정
- 특성은 6종을 균등 배분

## 4. 기록 규칙 (제출용)

**모든 PR 설명에 아래 3줄을 넣는다.** 이게 쌓이면 제출 문서가 자동으로 완성된다.

```
사람이 결정한 것:
Codex가 구현한 것:
해결한 문제:
```

추가로 `docs/DEV_LOG.md`에 하루 한 줄씩 남긴다. 막힌 지점과 해결 방식이 피치에서 가장 잘 먹히는 소재다.

**피치에서 쓸 서사 뼈대** (지금 미리 정해두고, 개발하며 근거를 채운다)

> 규칙 설계와 밸런스 판단은 전부 사람이 했고, 구현은 코어·UI·콘텐츠·검증 네 트랙으로 나눠 병렬로 돌렸다. 특히 카드 350장은 스키마와 분포 조건만 사람이 정하고 생산은 배치로 처리했으며, 자동 검증을 통과한 것만 머지했다.

이 문장이 진실이 되도록 개발한다. 반대로 하지 않는다.

## 5. AGENTS.md 템플릿 (저장소 루트)

```markdown
# AGENTS.md

## 프로젝트
재수학원 3파전 경영 시뮬레이션. 브라우저 웹 빌드. TypeScript + Vite.

## 절대 규칙
1. 실존 학원·강사·기업의 실명을 코드/콘텐츠 어디에도 쓰지 않는다.
2. `src/core/`는 순수 함수만 둔다. DOM·브라우저 API·Math.random() 금지.
3. 게임 규칙과 수치는 변경하지 않는다. 문제를 발견하면 수정하지 말고 보고한다.
4. 런타임에 외부 API를 호출하지 않는다.
5. 의존성 추가 전 반드시 확인을 받는다.

## 작업 방식
- 자기 트랙 디렉터리 밖의 파일을 수정하지 않는다.
- 변경 후 `npm run typecheck && npm run test`가 통과해야 한다.
- 콘텐츠 생성물은 `npm run validate:content` 통과 전까지 머지하지 않는다.

## PR 설명 형식
사람이 결정한 것: / Codex가 구현한 것: / 해결한 문제:
```

## 6. CLAUDE.md 템플릿 (저장소 루트)

```markdown
# CLAUDE.md

## 역할
코디네이터. 직접 대량 구현하지 않고, 스펙 정합성 유지와 태스크 분해, 리뷰를 담당한다.

## 참조 순서
01_GAME_DESIGN.md 가 규칙의 단일 출처다. 코드와 문서가 다르면 문서가 맞다.
02_TECH_SPEC.md 의 아키텍처 원칙을 위반하는 변경은 승인하지 않는다.

## 판단 기준
- 스코프 확장 요청은 00 문서 7절 스코프 가드와 대조한다.
- 밸런스 변경 제안은 사람에게 올린다. 임의로 반영하지 않는다.
- 마감이 가까울수록 "빼자"를 먼저 제안한다.
```

## 7. 하루 리듬

```
아침  : 어제 배치 결과 리뷰 → 오늘 트랙별 태스크 분해
낮    : 트랙 병렬 실행, 사람은 플레이 감각 판정에만 개입
저녁  : 머지 → 배포 → 직접 한 판 플레이 → DEV_LOG 한 줄
```

**매일 한 판은 반드시 직접 플레이한다.** 이걸 건너뛰기 시작하면 재미가 아니라 기능이 쌓인다.
